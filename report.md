# Отчёт о проделанной работе — mysh

Отчёт обновляется по ходу разработки. Текущее состояние: реализован только
лексер (фаза «строка ввода → поток лексем»), остальные фазы отсутствуют.

## Реализованные возможности базовой части

### Лексика — реализовано

- разбиение строки на слова и операторы по пробелам/табам;
- операторы `| & ; && || ( ) < > >>` с правилом максимального совпадения
  (`&&` распознаётся как один токен, а не как два `&`);
- перевод строки как отдельный токен (`NEWLINE`), завершающий список команд;
- комментарии `#`, начинающиеся в начале слова и вне кавычек;
- одинарные кавычки `'...'` — всё буквально;
- двойные кавычки `"..."` — буквально, кроме `\"`, `\\` и `\` + перевод строки;
- обратная косая черта `\` вне кавычек — экранирование следующего символа;
- `\` + перевод строки — продолжение команды на следующей строке;
- пустая пара кавычек `""`/`''` — аргумент нулевой длины;
- кавычки не разделяют слово (`a"b c"d` → одно слово `ab cd`) и удаляются
  из итогового текста;
- незакрытая кавычка и `\` в конце ввода — отдельные статусы ошибки,
  на которых интерактивный режим показывает вторичное приглашение и
  дочитывает следующую строку, а неинтерактивный считает это синтаксической
  ошибкой (код возврата 2).

Отладочный режим `--dump-tokens` выводит поток лексем и завершает работу,
как требует ТЗ; поддержаны обе формы запуска — `-c 'команда'` и чтение из
`stdin` (с приглашением `mysh> ` и вторичным `> ` в интерактивном режиме).

### Не реализовано

Все фазы после лексера отсутствуют:

- **синтаксис** — грамматика (`list`/`and_or`/`pipeline`/`command`/...) не
  разбирается, дерева команд (AST) нет, `--dump-ast` не реализован;
- **выполнение простой команды** — ни встроенные команды, ни `fork`/`exec`
  для внешних программ;
- **перенаправления ввода-вывода** — лексер выдаёт токены `< > >>`, но их
  обработка (включая форму `2>`, `>out echo hi` и т.д.) не реализована;
- **конвейеры** (`|`) — токен распознаётся, `pipe`/`dup2` не реализованы;
- **списки команд** (`;`, `&`) — токены распознаются, последовательное и
  фоновое выполнение не реализовано;
- **подоболочки** (`(...)`) — токены `( )` распознаются, `fork` для
  подоболочки не реализован;
- **встроенные команды** — ни одна не реализована;
- **управление заданиями** — таблица заданий, `jobs`/`fg`/`bg`/`wait`,
  группы процессов, передача терминала — не реализовано;
- **обработка сигналов** (`SIGCHLD`, `SIGINT`, `SIGTSTP` и др.) — не
  реализована;
- **режимы запуска `mysh` / `mysh -c` / `mysh < файл`** без флага
  `--dump-tokens` — не реализованы: пока есть только отладочный режим.

## Сознательные отличия от поведения bash

- **`\` в самом конце строки в неинтерактивном режиме.** У нас это всегда
  синтаксическая ошибка (`LEX_TRAILING_ESCAPE`, код 2). Настоящий bash
  ведёт себя непоследовательно даже сам с собой: `bash -c 'echo a\'`
  печатает `a\`, а тот же текст, поданный на `stdin` файлом, даёт `a`.
  Решили не повторять эту непоследовательность, пока не появится повод.
- **`NEWLINE` как отдельный токен.** В списке операторов грамматики ТЗ
  (`word`, `redirection`, ...) перевод строки отдельно не упомянут, хотя по
  тексту ТЗ он «эквивалентен `;`». Явный токен `NEWLINE` вместо точки с
  запятой выбран, чтобы при необходимости парсер мог взять другое дерево
  для последней команды (например, не требовать `;` в конце файла).
- **Расширения не делает лексер.** `$VAR`, `~`, `*` и другие подстановки
  сейчас проходят как обычные символы слова: `echo $HOME` даёт токен
  `WORD [$HOME]` без раскрытия. Ожидаем, что раскрытие — задача более
  поздней фазы (исполнителя или отдельного шага после парсера), а не
  лексера; в грамматике ТЗ подстановки тоже не описаны как часть лексики.

## Архитектура и разбиение на модули

Реализован только модуль лексера, в соответствии с конвейером фаз из ТЗ
(`Строка ввода → [Лексер] → ... → Код возврата`):

```
src/
├── lexer.h   — типы token/token_list, lex_status, интерфейс lex()
├── lexer.c   — реализация: разбор строки на токены одним проходом
└── main.c    — временная точка входа: CLI-обвязка --dump-tokens
```

- `lexer.h`/`lexer.c` не выполняют системных вызовов и ничего не знают о
  парсере — на входе строка, на выходе `token_list`, как того требует
  разделение фаз;
- `main.c` временный: на нём нет исполнителя, он нужен только чтобы
  показать работу лексера преподавателю (`--dump-tokens`) и будет заменён
  на настоящий главный цикл интерпретатора вместе с появлением парсера.

Модули `parser`, `executor`, `redirections`, `builtins`, `jobs`, `signals`
из рекомендованного ТЗ разбиения ещё не созданы.

## Сборка и запуск

```bash
make          # релизная сборка -> ./mysh
make debug    # со sanitizers (-fsanitize=address,undefined) и -g -> ./mysh-debug
make clean    # удалить собранные бинарники
```

Makefile сам определяет, принимает ли компилятор `-std=c23` или нужно
использовать `-std=c2x` (для gcc < 14); собирается `gcc` и `clang` с
`-Wall -Wextra` без предупреждений. Макрос `_POSIX_C_SOURCE 200809L`
задан в `Makefile` через `CPPFLAGS`.

Проверка лексера:

```bash
./mysh --dump-tokens -c 'echo "a  b" | wc -l'   # разбор одной строки
./mysh --dump-tokens                            # чтение команд из stdin,
                                                 # с приглашением mysh>/>
                                                 # в интерактивном режиме
```

## Известные ограничения и дефекты

- Утечки памяти не проверялись под `valgrind` (нет доступа к нему в среде
  разработки) — проверка пока ограничена `-fsanitize=address,undefined` и
  ручным фаззингом на случайных строках; `valgrind --leak-check=full
  --track-fds=yes` предстоит прогнать отдельно.
- Известных дефектов в реализованной части (лексер) на данный момент не
  обнаружено.
- Тесты (`tests/`) пока не написаны.
